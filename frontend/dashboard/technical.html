Methodology and implementation

Methods and code

How the tracker collects two independent counts, keeps every version, matches them voter by voter, and estimates party lean, with the caveats that bound each step.

Collector: Python standard library · checks every 15 minutes · append-only archive

01 · ARCHITECTURE

Collect, hash, keep everything

A small Python program runs every 15 minutes from cron. For each source it fetches the current file, takes a SHA-256 hash of the bytes, and writes a new copy only when the hash differs from the last one stored. Each new version is then compared against its predecessor and the difference is logged.

The archive is append-only. Several counties and the state overwrite yesterday's file at the same web address, so a version we fail to capture is lost permanently. Nothing is ever overwritten on our side, which is what makes the revision history possible.

# every 15 minutes, per source
fetch -> sha256(bytes)
if hash changed:
    write data/raw/<source>/<date>/<time>_<hash>_<name>
    diff against previous version -> changes.jsonl
02 · SOURCES

Two counts, eight counties

The state count comes from the Secretary of State's Civix early-voting report for election 53815. Each request returns a file whose contents are base64-encoded; we pull the turnout file for every early-voting date, plus the per-county voter rosters, every cycle.

The county counts come from each county's own site, in whatever form it publishes: PDF, spreadsheet, or HTML table. The formats differ by county, so each has its own parser. We label every county's figure with that county's definition of a counted vote, because they differ.

03 · ACCESS

Two counties fought the fetch

Two county sites block automated requests from data-center addresses. We did not disguise the collector to get around that, because misrepresenting an automated client as a person is the one line the project will not cross. Instead:

  • Dallas serves a CAPTCHA to addresses outside the United States. We route Dallas requests through a United-States server, which the site accepts.
  • Hays is behind a security vendor that blocks data-center and automated browsers outright, even a real one. We collect it by a supervised pull: a staff member opens the files in their own browser, which clears the check as a person, and a script reuses that same open session to save them. It runs a few times a day rather than every 15 minutes, which is the one coverage gap we have.

We have asked both counties to allow the fetcher through, which is a small configuration change on their side and closes the gap cleanly.

04 · MATCH

Comparing the rosters voter by voter

For each county we build the set of voter ID numbers in the latest version of every dated state roster, and the set in the county's own roster, then compare them. Three groups come out of it:

  • On both rosters: the large majority.
  • State only: the state records a vote the county's own list does not. This is the small group worth scrutiny.
  • County only: larger, and mostly ordinary. The county posts a day ahead of the state, and the state's roster begins October 14, so earlier mail ballots have no state roster row to match.

Every result is broken down by date and by method (in person or mail), because reading the raw totals without that breakdown overstates the gap. The latest day is nearly always "county only" simply because the state has not posted it yet.

All of this runs offline on files kept at owner-only permissions. The matching uses voter ID numbers; no names are read into the comparison, and only counts ever leave it. Nothing voter-level is published, logged, or committed to version control.

05 · PARTY LEAN

Estimating lean, and its ceiling

Texas has no party registration. The standard proxy is which party's primary a voter has chosen, so we build each voter's primary history from public rosters and from the state's voter-history file where an organization can provide it. A voter who has only ever voted in Democratic primaries is counted D, only Republican is counted R, a mixed record takes the most recent primary, and a voter with no primary record is left unclassified.

The ceiling is that last group. Between a quarter and a third of this year's early voters have no primary history, so no lean can be assigned to them. We report the lean only as a share of the voters we can classify, never as the whole electorate, and we show the unclassified share next to it so the blind spot is always visible.

# per voter, from primary history
only D primaries        -> D
only R primaries        -> R
mixed                   -> most recent primary
no primary on record    -> unclassified  # a quarter to a third of voters
06 · LEAD CHECK

Resolving the "state only" voters

For the small group the state lists that a county does not, we join each voter ID to the county registration file and report counts only: how many are currently registered, their registration status, and the year they registered. This separates an innocent explanation, a brand-new registrant voting for the first time, from a real anomaly, a voter ID the state says voted that the registration file does not contain.

In Travis County, of 184 such in-person voters on completed days, 103 had registered in 2026, 34 were in a routine address-check status but still eligible, and only 4 were absent from the registration file entirely. Those four are the only entries that warrant a closer look.

07 · LIMITS

What these numbers cannot do

  • Mail coverage. The state's voter-level roster starts October 14, so mail ballots returned earlier cannot be checked name by name through it.
  • Definitions differ. A check-in is not the same event as an accepted ballot. We label each county's definition so a gap is never read as an error when it is a difference in what is counted.
  • Lean is partial. It speaks only for voters with a primary record.
  • Hays is sampled. A few pulls a day, not every 15 minutes, until the county allows the fetcher through.
  • Unofficial. All figures are unofficial until each county canvasses and reconciles after Election Day.

The project's value is not a single verdict. It is that every number is captured with its source and its version, so a claim can be checked against the record instead of argued from memory.

09 · SOURCE BY SOURCE

Every source, start to finish

The table above is the index; here is each source in full — where it comes from, how it is fetched, how it is parsed, and the specific quirk each one forced us to handle. Three things are shared across all of them: every spreadsheet is read by a small standard-library reader that concatenates all worksheets, not just the first tab; every file is hashed so only a genuine change is ever stored; and the voter-by-voter match uses ID numbers only, on files held at owner-only permissions — names are never read into it.

Secretary of State

stateCivix EVR API · election 53815
What it is
The state's official early-voting feed. A plain request returns a small JSON wrapper whose payload is base64-encoded; we decode it. Two kinds: a turnout summary per early-voting date, and a per-county, per-date voter roster (one row per voter — an ID, and whether the vote was in person or by mail).
Collection
The turnout summary for every early-voting date through today is pulled each cycle; the rosters every half hour. Only changed versions are written, and nothing is ever overwritten — the state silently revises past days, and we want every revision on the record.
Parsing
From turnout we read registered voters and the in-person and mail totals per county. From each roster we take the voter ID and the method; for a given date we use the latest capture and union the IDs, so a revision adds voters rather than replacing the day.
Cross-checks
Past-day revisions are found by hashing each capture and diffing it against the one before — the revision timeline on the dashboard is built straight from those diffs. A date with no data yet returns an empty body, which we treat as "nothing yet," not an error.
Caveat
The voter-level rosters begin October 14, so mail ballots accepted before then have no state roster row to match against. A transient server error on a single date simply retries next cycle.

Harris

countyharrisvotes.com — Election Reports
What it is
Three files. EVPA_unofficial.pdf is a per-location table of in-person check-in counts (the "Total Early Voters" figure). Two zips hold the voter rosters: the early-voting zip and the ballot-by-mail zip.
Collection
Fetched directly every 15 minutes with a conditional request — the server is asked "changed since my copy?" and answers 304 Not Modified when it has not, so the multi-megabyte roster zip is not re-downloaded every cycle. The many 304s in the log are this working as designed.
Parsing
The early-voting zip holds ten daily CSVs plus a DISCLAIMER.TXT; we read every CSV and skip the disclaimer, taking the state voter ID and activity date from each. The mail zip is read the same way. IDs are unioned across all files.
Cross-checks
The ten daily files are summed, not sampled — reading only the first would under-count in-person voters by hundreds of thousands. The voter-by-voter numbers come from the roster zips, not the EVPA totals sheet.
Caveat
The EVPA check-in total runs ahead of the posted roster and of the state count: a check-in is the front-door event, not a reconciled, counted ballot.

Dallas

countydallascountyvotes.org — Nov 3, 2026 results
What it is
Two spreadsheets linked from the results page — an in-person early-voting details report (a state voter ID and the date voted) and a mail-ballot returns report (a voter ID and a return date).
Collection
Dallas serves a CAPTCHA to addresses outside the United States, so these requests are routed through a US server, which the site accepts. A conditional request keeps the ~50 MB roster from re-downloading when unchanged. The results page is read each cycle to find the current links.
Parsing
We locate the header row by its SOS VOTERID / DATE VOTED columns (their position varies) and read every data row. Dates arrive as either Excel serial numbers or M/D/YYYY text, and both are converted.
Cross-checks
Dallas renamed the in-person report mid-election (from In-Person-Early-Voting-Turnout-Details-Report to Early-Voting-Turnout-Details); our file-matcher accepts both names while still excluding the unrelated by-location summary. The rename briefly froze the county — which is how we caught it, as a one-day spike of ~42,000 phantom "state-only" voters.
Caveat
In-person is keyed to the date voted; mail to the return date.

Bexar

countyearlyvotecounts.bexar.org · DocumentCenter folder 245
What it is
A live totals page (current day only) plus a document library of dated per-voter PDFs — a daily in-person roster (name, voter ID, polling place, precinct) and a daily mail-ballots-received roster.
Collection
The library's index is built by JavaScript and exposes no file links to a plain fetch, so we discover files by number: a document's "View" link redirects to an address that spells out its type and date, and the file downloads from a separate image endpoint. We scan document numbers forward from the last one seen and fetch each new one once — the files carry no cache validator, and each dated file is final once posted.
Parsing
Each PDF is converted to text; every data row carries exactly one 8–11 digit voter ID, which we extract. All daily in-person and mail files are unioned, each voter dated by the file it appears in.
Cross-checks
This closed the last gap — Bexar was the one county with no voter roster, so its entire state-only figure had been excluded from the match. The 787-page days parse exactly like the short ones.
Caveat
The PDFs carry no per-row date, so the file's date is used; mail is received, not yet accepted.

Travis

countyvotetravis.gov — current election
What it is
A single zip, G26-Voter-Rosters.zip, that currently holds about fifty spreadsheets — a separate file per day for Early Vote, Ballot by Mail and Limited Ballot, plus mid-stream "UPDATED" re-issues of some days.
Collection
Fetched directly each cycle; the current-election page is also read to catch the roster link.
Parsing
We walk every file in the zip and key off its name: MM.DD.YYYY Early Vote and MM.DD.YYYY Ballot by Mail are read (voter ID in the first column), and their UPDATED re-issues are read too, because the name still begins with that date and type. IDs are unioned, each voter keeping the earliest date it appears on.
Cross-checks
Fifty files, three roster types and same-day corrections collapse into one clean per-voter set; a voter in both an original and an UPDATED file is counted once. Limited-ballot files are skipped on purpose — those records carry no voter ID to match.
Caveat
Limited ballots are not matched (no ID on the record).

Hidalgo

countyhidalgocounty.us — EV totals & rosters
What it is
A cumulative early-voting roster (CSV, with a voter ID), a cumulative mail-application list (spreadsheet) and a totals PDF.
Collection
The document index is fetched only once an hour, not every 15 minutes: the county's server returns "too many requests" if polled harder, and the link filters are deliberately narrow for the same reason.
Parsing
The early-voting roster is read by column name; the mail list's ID column is found by its header.
Cross-checks
The collector backs off on the rate limit; both rosters are cumulative, so the latest capture is the full set.
Caveat
The mail list is applications for a mail ballot, not returned ballots — a different thing from the other counties' mail figures, and labeled as such.

El Paso

countyepcountyvotestx.gov — current election
What it is
A cumulative in-person voter list (spreadsheet, voter ID) and a received-mail-ballots list (CSV with a received date), linked from the page and hosted on S3.
Collection
Fetched directly each cycle through the page's document links.
Parsing
In-person: the voter ID from the first column of the latest list. Mail: the voter ID and received date from the CSV.
Cross-checks
The in-person list is cumulative, so the latest "Day N" file is the whole roster.
Caveat
Mail is received, not yet accepted.

Cameron

countycameroncountytx.gov — election results
What it is
A county voter list (spreadsheet with a check-in date) and a mail list (spreadsheet with a ballot-received date).
Collection
Fetched directly through the results-page links each cycle.
Parsing
Voter ID in the first column, check-in date in the third; the mail ID and received date come from the mail file.
Cross-checks
Dates arrive in mixed formats (ISO text or Excel serial) and are normalized before the match.
Caveat
The in-person figure is keyed to the check-in date.

Hays

county · sampledhayscountytx.gov — Nov 3, 2026 election
What it is
An in-person check-in list published as a searchable web page (its rows embedded as data arrays) and an absentee-ballots-received file delivered as a zip of CSV and spreadsheet.
Collection
Hays sits behind a security vendor that blocks every automated client, even a real headless browser — and we do not disguise ours. A staff member opens the files in their own browser, which clears the check as a person, and a script reuses that open session to save them into an inbox the collector ingests. It runs a few times a day.
Parsing
The check-in page's embedded rows are read with a pattern that pulls the voter ID and the vote date; the absentee zip ships the same data as both CSV and spreadsheet, and we read one.
Cross-checks
Reading one of the two duplicate absentee formats avoids a double count, and the inbox hand-off keeps the human-in-the-loop step from touching the rest of the automated pipeline.
Caveat
Sampled a few times a day, not every 15 minutes, until the county allows the fetcher through — our one coverage gap.
10 · OPEN METHODS

Take these methods and run

Everything above is the whole method — there is no secret step. It runs on public county and state pages and the Python standard library, it keeps every version it fetches, and it reports counts with their source and date so any figure can be checked against the record instead of taken on trust.

Please copy it. Point the same approach at a county we do not cover, at a different race, or at another state's feed; run it next to ours and compare. Independent eyes on the same public data — from anyone, of any persuasion — is the entire point: a discrepancy that two or three trackers surface separately is far harder to wave away than one that only we report. If you replicate this and your numbers disagree with ours, tell us — a contradiction we cannot reproduce is a bug we want to find. There is a contact link on the dashboard.

The one line we hold is about people, not method: aggregate counts only, never voter-level data, and we never misrepresent an automated client as a person to get past a block. Full transparency about how; strict privacy about whom.
